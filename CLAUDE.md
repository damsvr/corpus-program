# CLAUDE.md — Corpus Program

SaaS Next.js 15 (App Router) + Prisma/Postgres + Auth.js (credentials, JWT) + Tailwind 4. UI en français, mobile-first.

## Ce que fait le produit
- 3 profils : `CROSSFIT`, `HYBRID`, `FUNCTIONAL` (enum Prisma `ProfileType`, `activeProfile` sur `User` ; teinte d'accent via `data-profile` dans `src/app/(app)/layout.tsx` et `globals.css` : rouge / jaune / orange).
- **Pas de génération IA dans l'app** (décision produit) : l'athlète utilise les agents de `docs/agents/`, relit, puis **importe le JSON** (`/import`). `src/lib/import-schema.ts` valide (erreurs bloquantes + avertissements), `src/lib/import-week.ts` écrit en base.
- Functional : 4 jours × 3 modules de 20 min (`Bloc.module` = CHARGE/VOLUME/MOTEUR) + 1 jour tampon (`Day.jourType = TAMPON`). Règles de placement : Charge en premier, Moteur ≥ 20 min après Charge (avertissement dans `/seance/[dayId]`). Complétion **par module** (`SessionLog.module`).
- Le JSON importé fait foi : contrat dans `docs/agents/01-schema-sortie-commun.md`. Toute évolution du contrat = mettre à jour ce fichier, `import-schema.ts`, les tests et les prompts d'agents ensemble.
- **Rôles et partage** : `User.role` = `COACH` (Damien — possède la programmation, seul à voir `/import`) ou `ATHLETE` (par défaut à l'inscription — suit la programmation du coach en lecture seule, garde son propre suivi). `src/lib/program.ts#programOwnerId(user)` résout QUI possède le `Program` à afficher (le coach lui-même ; pour un athlète, le coach qui a publié des semaines pour son profil actif, le plus récemment s'il y en a plusieurs) — **toujours l'utiliser** pour `getActiveProgram`/`getWeek`/les lookups de `Day` dans les pages et actions de séance, jamais `user.id` directement pour ça. En revanche `SessionLog`/`Prs`/`AthleteProfile`/`activeProfile` restent scopés à `user.id` (suivi et préférences personnels, même en suivant la programmation de quelqu'un d'autre). `Day.weekday` (planification) n'est modifiable que par le coach (`setDayWeekday` vérifie le rôle) puisque c'est une donnée partagée. Promotion COACH à l'inscription : `src/lib/roles.ts#isCoachEmail` (env `COACH_EMAILS`, replis sur l'e-mail fondateur) ; le compte fondateur existant a été promu via la migration de données `promote_founder_coach`.
- **Accès gratuit par lien** (préparation TyRun) : un `AccessLink` Hybrid unique, réglé par le coach dans `/profil` (nom du cycle, blocs `blocDebut`–`blocFin`, date de fin incluse, inscriptions ouvertes/fermées). `/acces/[code]` inscrit l'athlète avec `accessLinkId` : profil verrouillé (pas de quiz, `setProfile` refusé), et `getAccess(user).weekWhere` (`src/lib/access.ts`) restreint **toutes** les lectures de semaine/jour (`getActiveProgram`, `getWeek`, lookups de `Day` en séance) aux blocs du cycle ; après `endsAt`, plus d'inscription ni de programme (écran « Cycle terminé »), l'historique reste. Toute nouvelle page qui lit des semaines doit passer ce filtre. Ces comptes ne sont pas à facturer quand Stripe arrivera. Inscription par lien : nom obligatoire + case **décochée par défaut** « être recontacté » (`marketingOptIn`/`marketingOptInAt`, RGPD, révocable dans `/profil`) ; le coach voit les inscrits dans `/profil` et exporte en CSV (`/api/acces/contacts`) **uniquement** ceux qui ont accepté. Contact Instagram du coach (`src/lib/contact.ts`) affiché aux inscrits du lien (invitation, Aujourd'hui, Profil, fin de cycle).
- **Semaines** : `Week.numero` n'est que le rang d'import (unique par programme, sert dans `?w=`) — ne jamais l'afficher ni s'en servir pour l'ordre. Libellé = `weekLabel` (« Bloc 1 · S2 »), ordre et « semaine en cours » = (`blocNumero`, `semaineDansBloc`) via `compareWeeks`. Une S2 importée avant la S1 s'appelait « Week 01 » et paraissait absente. Le coach voit dans `/profil` ce qui est publié par profil et combien d'athlètes le suivent (`getPublicationStatus`).
- **Partage de séance** : `/partager/[id]` (lien « Partager » dans `/historique`) génère une carte façon Strava via `src/app/api/share/[id]/route.tsx` (`next/og`, polices Poppins dans `src/assets/fonts`, licence OFL). **Charte DS Coaching** : anthracite `#2d2d2f` (fond exact du logo `src/assets/brand/ds-coaching.jpg`), dégradé `#ffc533 → #ff3d2b`, « CORPUS PROGRAM » mis en avant, pictogrammes au trait dessinés dans la route. Options (`src/lib/share-card.ts`, testé, passées en query) : fond DS / photo de l'athlète / sticker transparent, story 9:16 ou post 4:5, commentaire (≤ 140 car.), données affichées (durée, kcal, perfs), jauges 1–5 **Intensité** et **Satisfaction** (points seuls sur la carte, pas d'adjectif ; non enregistrées en base). Avec photo, la route ne renvoie que le calque transparent et **le navigateur compose photo + calque dans un canvas** : la photo ne quitte jamais le téléphone. Contenu : profil, pattern du jour (`detectPattern` : force / gym / haltérophilie / autre), durée, calories **estimées** (MET × poids de corps des PR, 75 kg par défaut), performance selon le pattern (`src/lib/share.ts`, testé). Boutons réseaux (Instagram, Facebook, WhatsApp, Snapchat, TikTok, X) : sur mobile ils ouvrent la feuille de partage native (Web Share API — un site ne peut pas viser directement une story Instagram, il faudrait une appli native), sur ordinateur ils enregistrent l'image et ouvrent le site du réseau ; le commentaire est copié pour la légende. L'image est préparée avant le clic (Safari refuse `navigator.share` après un téléchargement asynchrone).
- **Chronos de séance** (`/seance/[dayId]`, `runner.tsx` + `bloc-run.tsx` + `timers.tsx` + `wod-clock.tsx`) : `classifyBloc` → échauffement (chrono global), mobilité (un chrono par série/côté pour les tenues « 30'' »), WOD (`parseWodFormat` : EMOM / Every X / AMRAP / for time), travail. Un bloc de travail se présente comme sur les notes du coach (`planBloc`) : **interval** (« N rounds, Every X:XX » / EMOM) = « N rounds · un toutes les X:XX », gros « Démarrer », puis compte à rebours du round avec « Round k / N » (les rounds écoulés sont validés automatiquement) ; **sets** (un mouvement ou un superset en N×M, `restGroups`) = « N séries de : », gros chrono + « Série k / N » + bouton « Série terminée » (valide tous les mouvements de la série, enclenche le repos du groupe, « Série précédente » pour corriger) ; **sequence** (mouvements indépendants : montée en charge, séries mixtes) = lignes par exercice avec « Fait ? » et repos par groupe. Il n'y a **pas de chrono par mouvement** dans un bloc de travail (décision du coach) — seulement en mobilité (`parseHoldSeconds`, jamais les distances « 20m »). kg/reps se saisissent sur la série en cours. Les boutons de chrono ignorent les doubles appuis (`usePressGuard`) et l'écran est grisé tant que la page n'est pas hydratée. **Ne pas ajouter de `loading.tsx` dans `(app)`** : le Suspense de streaming a retardé/empêché l'hydratation du runner (boutons morts) en dev comme en prod.
- **Présentation des séances** (inspirée de Functional Bodybuilding, charte navy + accent de profil conservée) : une séance = sections plates séparées par un filet, chacune avec `BlocHeader` (étiquette « BLOC A », gros titre accentué, « 16 min · 5 séries » / « 4 rounds · toutes les 03:00 » / « AMRAP 13 min » via `blocStructure`, note repliable « Lire plus ») puis des `ExerciseCard` (vignette vidéo `MovementThumb`, nom en capitales, reps en accent, charge/repos en retrait, précisions du coach en détail). Mouvements enchaînés = `ExerciseGroup` avec filet d'accent (« Circuit · 4 rounds », « Superset · 5 séries », `movementGroups`). Même rendu sur Programme (`BlocCard`), Séance (`runner.tsx`) et WOD. Les séries ne sont jamais accolées aux reps dans un bloc de travail (`prescription` retire le « N× », sauf échauffement/mobilité).
- **Vidéos des mouvements** : chaque mouvement (programme, séance, WOD) a un bouton ▶ (`VideoButton`, contexte `VideoProvider` chargé dans `(app)/layout.tsx`). Clé = `movementKey(nom)` (sans accents, casse, « — tempo… », « (RX) »), donc un lien enregistré vaut pour toutes les semaines, présentes et futures, sans rien ajouter au JSON des agents (ne pas leur faire inventer d'URL). Table `MovementVideo` gérée par le coach dans `/videos` (liens YouTube validés par `parseYoutube`, départ `t=` conservé) : lecteur intégré `youtube-nocookie` ; sans lien, ▶ ouvre la recherche YouTube du mouvement (`youtubeSearchUrl`).
- **Feedback au coach** : à la fin d'une séance l'athlète peut laisser un feedback écrit et/ou vocal (`feedback-box.tsx`, `SessionLog.comment`, table `SessionVoiceNote`, audio ≤ 2 min / 1,5 Mo, 32 kb/s, envoyé après l'enregistrement de la séance par `POST /api/voix/[sessionId]`). **Privé : seul le COACH le lit et l'écoute** (`/retours`, lecture audio réservée au coach, requêtes `Range` gérées pour Safari) ; l'athlète ne le revoit pas, l'historique indique seulement « ✓ Feedback envoyé au coach ». Ne jamais l'afficher ailleurs (partage, autres athlètes).
- **Limite connue** : les charges affichées (ex. « 70% TM ») viennent du JSON importé par le coach, calculées sur SES PR à lui — l'app ne recalcule pas encore les % en kg pour chaque athlète à partir de ses propres PR. À construire si la personnalisation par athlète devient nécessaire.

## Règles métier codées ou à respecter
- ≈ 300 min/semaine pour les 3 profils ; séance ≤ 90 min (erreur au-delà) ; CrossFit 70–86 min (avertissement).
- CrossFit/Hybrid : 4 séances, pas de jour tampon ni de champ `module`. Hybrid/Functional : pas d'haltérophilie à la barre (avertissement sur les noms d'exercices).
- Charges exprimées en %TM / %PDC à partir des PR de `Prs` (l'agent les calcule ; l'app n'affiche que du texte).

## Local
- `npm run db:dev` (Postgres embarqué, port 5433, `.data/`), `npm run db:migrate`, `npm run dev`. Tests : `npm test`.
- Ne jamais saisir de mot de passe réel dans un navigateur piloté par Claude. Pour tester l'UI connecté : créer un utilisateur synthétique en base et forger un cookie de session `authjs.session-token` avec `next-auth/jwt` (`encode`, salt = nom du cookie, secret = `AUTH_SECRET`).
